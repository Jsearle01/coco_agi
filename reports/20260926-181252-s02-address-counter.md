### 3 — Reasoning

**3.1 §3's pre-start checks were performed and one of them paid immediately.** The fill instrument was
read before being trusted (§3.1) and found correct — but it was still **untested code by definition**,
and four defects surfaced when it first ran (§7.2). The sampler stayed `scr:pixels()` (§3.2); the
adjudicator was already reordered in S-01 (§3.3); liveness is measured within one sample window (§3.4)
**and is what identified two of the four defects.**

**3.2 §2H's three checks.** (1) *A second mechanism for a different object class?* Yes and it is
load-bearing: **the FILL's stride (80 B/row) and the DISPLAY's stride (40 B/row below the switch) are two
different strides over one buffer**, and the whole question is how they relate. Reading only one of them
gives no answer. (2) *The calling routine.* The stride below the boundary is not chosen by the write —
it is chosen by the per-scanline recorded `$FF99` that S-01 found, and the counter is advanced by the
raster, not by the CPU. (3) *Grep the prior record.* S-01's NOTES supplied the mode pair, VOFFSET, the
eight eliminated hypotheses and the palette-refresh requirement; **none was re-derived** (§2).

**3.3 Granularity, stated because it bounds the claim.** Row *N* is filled with byte value *N* in all 80
of its bytes, so a displayed row reports **which 80-byte block** it read — not which byte. ★★★ **That is
sufficient for §1.1's enumeration and insufficient for byte-level questions**: if the counter runs on at
40 B/row, consecutive displayed rows advance half a block, which shows as the same value twice then +1.
**The signature is what distinguishes the cases, and it does not require byte precision.**

**3.4 Authority tier.** MAME 0.281, 4-colour pair, one configuration, `poke` launch. ★★★ **A pass here
is "worth building on", never proof about silicon** [S-01 §3.4: two GIME revisions, the later with
changed video timings]. **No hardware claim is made.**

### 6 — Reactive deviations and route accounting

1. **The fill was converted to a SUBROUTINE with a host-triggered refill**, not in the spike. Rationale:
   the decode needs a colour→index map, and deriving it from the CoCo3 palette byte would import an
   unchecked assumption about MAME's RGB conversion. **Calibrating in the same session removes the
   cross-run comparison that caused S-01's entire mess.**
2. **The palette flip was moved to a host-selectable register** (`s01_palreg`, default `$B1`,
   unchanged for S-01's arms). Forced by §7.1: the screen needs a *changing* palette value while the
   decode needs the displayed four to *hold still*, and those collide on `$FFB1`.
3. **`s01_col0..col3` were added**, decoupling the displayed palette from the flipping pair. The old
   coupling made two indices identical and **calibration refused to run** — the right behaviour, and the
   reason this was found before any decode was believed.
4. **§4C's extra splits were added to mode 1** behind `s01_dly2`/`s01_dly3`; zero preserves S-01's
   stage-1 behaviour exactly.
5. **Not done, and not asked for:** stage 2's FIRQ (§4C explicitly excluded it), the 16-colour pair.

**ROUTE ACCOUNTING.** I proposed, in reporting S-01, that §3.2 was "the natural next step" and that no
layout decision should precede it. **That is what this spike did, and the answer removes the blocker
rather than complicating it.** I also predicted the signature ("the value advances every two rows if the
counter runs on") **before running it**, and it is what appeared — recorded here because a prediction
stated in advance is worth more than one fitted afterwards.

### 7 — Uncertainty flags

**7.1 ★★★★ A CORRECTION to S-01 §7.3 — the conclusion stands, the test did not.** S-01 concluded the
bitmap stays current only while a **palette** value changes. **The working run had changed both the
palette and `$FF99`, so the separating arm was missing.** It has now been run: **`$FF99` changing with
the palette held constant leaves the screen broken.** So a changing palette value is required and
`$FF99` traffic is not a substitute. ★★★ **S-01's attribution was right and under-tested — which is
precisely the failure S-01 §7.3 is about, committed one spike later in the same file.**

**7.2 Four defects in the instrument** (§3.1 predicted them; two are worth carrying):
- ★★★★★ **A subroutine placed in a fall-through path, twice.** `s01_palwr` sat immediately after the
  `bsr` that called it, so control fell back in and ran `puls b,pc` against nothing; relocating it put
  it in the **init's** implicit fall-through to `s01_loop`, so the init filled twice and `rts`-ed to
  `$8006`. ★★★ **The cure is an explicit `bra s01_loop`, not a better address** — the init reached the
  loop by falling through, which was correct only while nothing sat between them.
- ★★★★ **The host poked init-consumed parameters AFTER setting PC.** A race, not a typo: the guest
  starts executing immediately and had already filled and set its palette from the defaults. **A poke
  after handover works only for values the LOOP re-reads.**
- ★★★★ **The displayed palette was coupled to the flipping pair**, making two indices identical.
- ★★ **Short branches out of reach** once §4C's block was added; made long rather than marginally short.

★★★★★ **What found the first two was `s01_frames = 0` beside a correct framebuffer and a correct
palette** — the liveness witness naming the *guest* rather than the display — **and then PC and S.
`S = $2F00 + 8` is what said "a return with nothing pushed."** Two hypotheses about the palette had
already been spent. ★★★ **The witness earned its place twice across two spikes.**

**7.3 An unexplained off-by-one, recorded so a layout designer does not trip on it.** The mapping above
the boundary is `src = y - 24`, i.e. **the first active scanline (y=25) shows source row 1, not row 0.**
★★ Not chased: it does not affect the stride question, which is what the spike asked. ★★★ **But anyone
computing a buffer offset from a scanline number needs to establish this independently** — it may be
VSCROL, a border-row definition, or an artefact of where the active area is measured from.

**7.4 Scope.** 4-colour pair, one delay set for §4A, one delay triple for §4C, one emulator. ★★★ **§4C
answers "do three writes work at all", NOT "are they stable"** — the spike said so and stage 2 is
untouched. ★★ Nothing here measures jitter over minutes, a FIRQ-paced boundary, or CPU time left to the
program.

### 8 — Follow-up candidates

1. ★★★★★ **Stage 2 — FIRQ precision — is now THE binding question.** §4C makes message boxes feasible
   and makes their *placement* the risk: a boundary that jitters by a scanline moves a box edge every
   frame. S-01 measured 2 of 19 delays jittering by one scanline on a busy-wait; **a FIRQ off the
   horizontal-border interrupt is the mechanism the spike specified and it is unbuilt.**
2. ★★★★ **The 16-colour pair `$1E`/`$16`** — the port's real target. Needs a 30,720-byte buffer that
   crosses `$8000`, forcing all-RAM mode and putting the 6809's vectors in RAM (S-01 §6.4 records why
   the spike avoided it). **Case 1 and the three-split result both need confirming there.**
3. ★★★★★ **THE MAP RULING NOW HAS ITS PRIZE, and my arithmetic is UNVERIFIED (§8's rule).** At 160
   physical the visual plane is 13,440 B = 1.64 slices and **fits inside two adjacent 8 KB slots**, so
   plane remapping during a composite **stops existing** rather than being batched. §1 of S-01 prices
   that at **47.5 cycles/pixel, 24% of the blit**; T-P0-157 measured `composite` at **59.4% of a steady
   cycle**, giving **≈14% of a cycle from plane access alone**, before the halved clear, present, restore
   and fill spans. ★★★ **An order of magnitude more than the interpreter work has yielded** (P6.102:
   3.85% across four changes; P6.103: 0.387%).
4. ★★★★ **The blit must move to span writes in the same task**, not a later one: at 160 an isolated
   pixel is a read-modify-write, and P6.89 measured opaque runs at 1.84.
5. ★★★ **The 40-column text is preserved by the split** — `TXT_COLS equ 40` needs 320 physical pixels at
   an 8-pixel font, and the split gives 320 for the text rows and 160 for the picture rows. **Now
   demonstrated rather than assumed, including the three-boundary case AGI's message boxes need.**
6. ★★★★ **A pool row is OWED for S-01's §7.3 finding** — *a control that holds a variable constant can
   delete the mechanism under test* — **and S-02 supplies its second instance** (§7.1: the same file,
   one spike later). ★★ Flagged in S-01's report §10 and still unwritten.
7. ★★ **The off-by-one in §7.3 of this report**, if a layout is ever computed from scanline numbers.
8. ★ **`fix_mojibake.py` remains red on a clean tree with a destructive repair** [T-P0-157 §4F],
   presented to Jay and **not yet ruled on.** Unrelated to this spike; carried so it is not lost.
