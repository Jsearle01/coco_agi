### 3 — Reasoning

**3.1 ★★★ AC-4, AND THE OFF-BY-ONE IT CAUGHT — which is the most useful thing in this report.**
The first draft of the generator wrote `args[i + 1]` and `cmds[i - 1]`, on the assumption that
opcode 0 is `return` and the table therefore starts at opcode 1. ★★ **`dispatch.py` settles it:
`self.commands[i] = Opcode(i, name, ...)` — the index IS the opcode**, and `V2_COMMANDS[0]` is
opcode `0x00`.

★★★ **Every handler would have been wired one opcode off. Every argument count would have been
one place off. Nothing would have raised** — the diff would have diverged at cycle 1 and pointed
at a variable, not at a table.

★★ **The lesson is sharper than "generate, do not type".** The constants were generated, from a
generated source, from the pin — and the defect was in the **index base**, which no amount of
generation protects. ★ So the generator now **cross-checks its entire opcode→name mapping
against `dispatch.py` and refuses to emit on disagreement**:

```
indexing check: OK -- 183 commands and 20 tests agree with dispatch.py, index == opcode
```

★ Confirmed independently against the measured coverage: `0x01 increment`, `0x02 decrement`,
`0x27 get.posn`, `0x07 isset`, `0x0C controller` all land where execution says they should.

**3.2 ★★★ AC-5's scope, measured by executing the reference.**
`vm_opcov.py` wraps every bound handler in the reference's dispatch table and counts
**executions**, not static occurrences — an opcode in a LOGIC that is never reached is not
exercised, and implementing it would be work the gate cannot check.

```
77 commands + 9 tests executed across KQ1/KQ2/KQ3 at 600 cycles each
   52 commands + 9 tests  implemented -> need real 6809 handlers
   25 commands            modelled    -> a DECLARED no-op
```

★★ **The three-way classification is taken from the REFERENCE, not re-decided here.** AC-5
forbids a silent no-op for an *unimplemented* opcode; it does not forbid a *declared* one for a
*modelled* opcode whose only effects are presentation. **Taking the line from `dispatch.py`
means the two VMs cannot disagree about which opcodes are allowed to do nothing.**

★★★ **Unimplemented opcodes reach `vm_op_unimpl`, which halts and records the opcode and the
logic that used it.** There is no `default:` that no-ops.

**3.3 ★★ The interpreter core, and design §5 confirmed rather than assumed.**
`vm_run_logic` is transcribed statement for statement from `cycle.py`: `0xFF` → condition block,
`0xFE` → **signed 16-bit little-endian** goto with `ip += 2 + off`, `0x00` → return, else a
command whose arguments are consumed by the **generated** count. `vm_test_if_code` carries the
full state machine — `0xFC` first entering OR mode and second ending a failed OR expression,
`0xFD` applying NOT to exactly one test, and the branch word consumed on the taken path.

★ **L-40 is live here and is marked in the source:** the goto offset is **signed** while the
coordinate compares are **unsigned** (`bhs`/`blo`). Mixing them is precisely what L-40 names.

```
core + generated tables : 1,978 bytes
generated tables         : 1,536 bytes  (256 + 256 + 512 + 512)
★ the interpreter itself : ~442 bytes
```

★★ **Design v1.0 §5 predicted "a few hundred bytes" for the dispatch. That is now measured, not
quoted.**

**3.4 ★★★ WHY THE TASK IS BIGGER THAN §2 FRAMES IT — the dependency, measured.**

```
LOGIC per title:  KQ1 133,428 B / 90 logics   KQ2 129,353 B / 133   KQ3 237,663 B / 125
largest single logic: 10,428 B (KQ3)
```

★★★ **133–238 KB cannot be resident in a 64 KB CPU window.** That confirms the design's
*"current LOGIC"* singular and makes a demand-load path mandatory. ★ **It fits in 512 KB via the
MMU, so trigger 5 does NOT fire** — but it is real work the dispatch did not scope, and it must
exist before a single handler can be gated.

★★ **And LOGIC is not the only resource.** Reading the reference's handler bodies for exactly
the executed set:

```
cmdSetView      -> vm.set_view(), which reads a VIEW resource for numLoops/numCels
cmdGetPosn      -> object x/y, populated from those resources
cmdNewRoom      -> resets objects, vars and flags across all of it
get_var(timer)  -> runs the in-game clock on four variables
```

★★★ **So the first gated handler needs: LOGIC demand-load, VIEW demand-load, an object table
fed from view data, and the timer model.** ★ **That is the honest shape of the remaining work,
and it is why this report stops here rather than presenting a VM that has never been diffed.**
