loop is written, the next destination address is prev+1.** A whole-picture copy is one run of
26,880 bytes. **A drawing operation breaks at every row, because each row is a separate
primitive with its own setup. The runs stop dead at one row, 152 times, and never once cross.**

### 3 — Reasoning

**3.1 ★★ L-47 first: is 26,880 bytes the right thing to look for?**
Not assumed — derived from Sierra's own measured register value. `VRES = $1E`, recorded in
T-P0-016, decodes as **HRES=111 → 160 bytes per row, CRES=10 → 16 colours at 2 pixels per byte,
LPF=00 → 192 lines** `[ref: GIME-RM §6 VRES]`. So their screen is **160 × 192 = 30,720 B**, and
an AGI room (160 × 168 logical pixels, doubled to 320 across) is **160 × 168 = 26,880 B**, one
byte per AGI pixel. ★ **The dispatch's figure is confirmed against their hardware state, not
adopted.** ★★ **§2.2 disclosure: `coco_agi`'s `docs/ground-truth/` is EMPTY; the GIME manual
was read from POP3_port's copy** (read-only sibling use, §2G). **Orchestrator-unverifiable.**

★ Enumerated across shares, regions, the RAM device and the GIME before concluding it (§2A.5).

**3.3 The instruments, and why the first can settle it alone.**
An AGI picture is **vector commands** — lines, strokes and floods in resource order, i.e.
arbitrary spatial order. A memory copy walks addresses upward. So every CPU write is classified
against its predecessor — `seq` (prev+1), `asc` (>prev), `other` (≤prev) — with the longest
consecutive run recorded per frame. ★★ **This is independent of where anything lives and of
what the MMU has mapped, which is exactly the weakness the search turned out to have.**

**3.4 ★★★ WHAT THE SEARCH COULD AND COULD NOT SEE — AC-3, stated because a negative is only as
good as its coverage.**

The MMU map recorded at every snapshot was constant: `00 3E 3E 09 01 02 03 3F` (slots 0–7,
8 KB each, physical block = value × 8192).

```
slot 0  $0000-$1FFF -> block $00  physical $00000
slot 1  $2000-$3FFF -> block $3E  physical $7C000   ★ same block as slot 2
slot 2  $4000-$5FFF -> block $3E  physical $7C000   ★ an ALIAS -- the same 8 KB seen twice
slot 3  $6000-$7FFF -> block $09  physical $12000
slot 4  $8000-$9FFF -> block $01  physical $02000
slot 5  $A000-$BFFF -> block $02  physical $04000
slot 6  $C000-$DFFF -> block $03  physical $06000
slot 7  $E000-$FFFF -> block $3F  physical $7E000
```

★★★ **The displayed framebuffer is at physical `$76000`** (VOFFSET `$EC00` × 8, logged at
f08275) **and spans `$76000`–`$7D7FF` = blocks `$3B $3C $3D $3E`. Only `$3E` is mapped.**
**So at most 8,192 of the 30,720 displayed bytes — 27% — were ever in view, and two CPU slots
were showing the same physical block.**

| | searched | not searched |
|---|---|---|
| **physical RAM** | **7 distinct blocks = 57,344 B** | **the other 57 blocks — ~89% of 512 KB** |
| **the framebuffer** | 8 KB of 30 KB | **blocks `$3B $3C $3D` — 73% of the display** |
| **timing** | 4 instants per transition | between them |
| **task context** | whatever OS-9 had mapped at the notifier | **the interpreter's own task, if different** |

★★ **A shadow buffer could have been in any of the 57 unmapped blocks and this search would
never see it.** ★★★ **That is trigger 3 and I am reporting it rather than dressing the result
up as a clean negative.** ★ The reason the window was still the right place to look — *a
memory-to-memory blit needs both ends mapped at once, so a buffer the 6809 copies from is
CPU-visible at that instant by construction* — **is an argument, not a proof, and it is now
moot: AC-4 shows there is no copy at all.**

**3.5 ★★ A false positive in my own signature, caught before it was reported.**
The search flagged `$0C00-$37FF` (11,264 B), `$4000-$57FF` (6,144 B) and `$6000-$77FF`
(6,144 B) as **100% "picture-shaped"** by the nibble-doubled test. ★★★ **`$00` has equal
nibbles, so cleared memory scores 100%.** Checked:

```

$0C00-$37FF   11264        40        $00    74%   cleared/uniform, not a picture
$4000-$57FF    6144         9        $00    54%   "

```

★★ **A rendered room must differ substantially between two different rooms. These do not.**
★ **The nibble-doubled test needs a distinct-value floor to be worth anything, and did not have
one.** Recorded because the signature looked decisive and was not.

**3.6 ★★ What the two phases actually look like — bearing on AC-5.**
The run-length signature differs sharply between the phases, and so does the address profile:

```
DISK phase   229 frames whose longest run is EXACTLY 256 bytes  <- ★ the sector size
             writes: $7000-$7FFF 57.8%,  $0000-$0FFF 17.2%,  $8000-$8FFF 9.8%
DRAW phase   152 frames whose longest run is EXACTLY 160 bytes  <- ★ one picture row
             writes: $0000-$0FFF 32.0%,  $1000-$1FFF 28.4%,  $B000-$BFFF 7.6%
```

★★ **256-byte runs are sectors landing in a buffer; 160-byte runs are picture rows.** The two
phases write different regions with different signatures, in sequence. ★ **This supports

independently confirms T-P0-015's correction that **`$7000` is the sector buffer, not the draw

### 6 — Reactive deviations, route accounting, and AC-7 (what I think it means)

> **Sierra draws straight to the visible screen, one row at a time, after the load completes.

★★ **What the row-shaped writes do and do not tell us.** They say their renderer completes
**full 160-byte rows as single sequential operations, 152 times across six transitions**. That
is consistent with a span-oriented fill. ★★★ **But it does NOT establish that their fill differs

spans, just rarely.* **Their figure is a per-frame maximum and ours is a per-span distribution.
The two statistics are not comparable, and treating them as comparable would be the over-read
this thread keeps producing.**

★ **So the lever I still believe in is the one from our own counters, not from Sierra:**
**3.09 boundary tests per pixel written** [T-P0-016 §6, from T-P0-013/014's recorded counters].
That is measured on our code, it needs no assumption about theirs, and it is testable directly.

★★ **And a genuine negative worth stating: this task looked for a technique we could adopt and
