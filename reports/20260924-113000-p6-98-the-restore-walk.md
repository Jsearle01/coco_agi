### 3 — Reasoning

**§3(2) — the four routines, in full.** `prp_visual` per row: `cmpa #PIC_H` skip · `mul` for
`row × 160` · `pshs d`/`clra`/`ldb`/`addd ,s++`/`std` for `+ x` · `lda p3rp_w`/`sta p3rp_n` ·
`jsr prp_split` · **two** map sequences (`lda #blk`/`sta ph_blk_fb`/`lda p3rp_slice`/`jsr`) ·
`jsr prp_copy`. `prp_copy`'s inner loop is `lda ,x+`/`sta ,u+`/`decb`/`bne` = **17 cycles/byte**,
behind a ~45-cycle preamble that includes the 32-bit `p3_restbytes` accounting.

★★★★ **The PRIORITY path is a different shape and was NOT changed**: `prp_priority` is packed, 80
bytes a row, and **deliberately over-restores by up to one pixel at each edge** — safe only because
every rectangle is restored before any sprite is composited. ★★★ **It still re-maps per row**, which
is why AC-4b leaves the priority plane byte-identical. §7(2).

**§3(3) — are `phase_draw_fb`/`phase_draw_fb_slot5` idempotent? NO.** They compute a block from the
slice and `ph_blk_fb` and call `phase_slot5`/`phase_slot6`, which store **unconditionally**. ★★★★
**So a re-map to the slice already mapped costs the whole sequence** — which is what C avoids, and it
avoids it at the *caller*, so the `jsr` goes too. ★★ Making the owner idempotent would have saved
only the register write (~5 of ~50 cycles).

**§3(4) — every caller of `prp_copy`:** `prp_visual` and `prp_priority` only. ★★★ **The box restore
does not share it** — `p3_restore_box` walks shadow→visible itself — **so `p3b_box` was not at risk,
and it is green.**

**§4A — the decomposition, before either change.** From P6.97's stage-9 profile at the same window:
`prp_copy` 11.1% · `prp_priority` 3.8% · `prp_visual` 3.1% · `prp_split` 2.3% · the four
`phase_draw_*` 2.4% = **22.7% of the stage**, which at 203,610 cycles/game-cycle and 1,107 bytes is
**41.8 cycles/byte**, splitting **copy 11.1% → 20.4** and **setup 11.6% → 21.3**.

★★★★ **The copy measures 20.4 against a 17-cycle inner loop** — the extra 3.4 is the preamble
amortised over ~13 bytes, and it is the same overhead that later capped B's gain.

**Authority tier.** Every figure is measured in this tree at a measured clock (1.789772 MHz). ★ The
10.5 cycles/byte comparator is **tier 2** — P6.96's measurement of Sierra's own bus — and §1 is right
that it is what a 6809 long copy costs; **it is not what a 6-byte copy costs.**

**§2H's three checks.** (1) *A second mechanism for a different object class?* ★★★★★ **Yes:
`prp_priority` is packed and over-restores by design, and is not the same shape** — §3(2). Changing
`prp_visual` alone is why AC-4b's priority plane is untouched. (2) *The calling routine.* The cost
was per-**row** setup on a 6–42 byte span, so the fix belonged in the row loop's caller, not in the
copy. (3) *Grep the reports.* P6.97 (the class table), P6.96 (10.5 cyc/B), P6.33/T-P0-088 (`ldd`
clobbers B, **in this routine's own header**), P6.84 (a share is not a cost) all agree and P6.97's
restore row needed correcting.

**§2S.** No sibling claim is made.

### 6 — Reactive deviations and route accounting

1. ★★★★★ **I mislabelled `-RestoreNoCross` as a fault arm in its own switch comment.** It removes the
   *skip*, so it re-maps every row — **it is the BEFORE arm and is behaviour-identical by
   construction.** ★★★ Corrected in the file, and AC-4's second fault arm built separately as
   `-RestoreStaleSlice`. **A before arm and a fault arm are opposites and I had written one comment
   for the other.**
2. ★★★★★ **My span arithmetic was wrong and the fault arm caught it.** I reasoned that a 4–32 row
   rectangle cannot cross a 51.2-row slice, so the crossing test was defensive. **It is not** — the
   stale-slice arm changes the visual plane. ★★★ **Reported rather than quietly benefiting from
   being right by accident.**
3. ★★★★ **B's predicted gain was revised down before it was built** and it still under-delivered:
   ~1.9 cycles/byte against ~5. §4A's span-width arithmetic is why, and it is now in the source so
   the next reader does not re-derive 17→10.5 as a per-byte saving.
4. ★★ **The priority path was not changed.** §3(2) found it a different shape (packed, over-restores
   by design) and §6's sixth trigger says to say so rather than assume it matches. §7(2).
5. ★ **The median could not measure either change.** It is quantised to 1/60 s; the write-tapped
   stage timer was used instead, and both are reported.

**ROUTE ACCOUNTING.** I told Jay to expect single digits, possibly imperceptible while moving,
nothing left behind, nothing else changed — **all four held.** What this contains: the 16-bit copy,
the crossing test, four arms, and three comment blocks. What it does **not** contain: any change to

### 7 — Uncertainty flags

1. ★★★★★ **The floor is not 10.5 cycles/byte at these span widths, and the dispatch's 4.4× headroom
   never existed.** At 6–42 bytes both halves are dominated by per-call and per-row overhead.
   ★★★★ **The remaining route is fewer calls, not faster loops** — restoring larger spans, or not
   restoring at all where P6.88's skip already applies.
2. ★★★★ **`prp_priority` still re-maps per row** and is ~⅓ of the bytes. **The same hoist should
   apply**, but it is packed and over-restores by design, so it is not a copy of this change.
3. ★★★ **`prpv_lastsl` is a loop-scoped cache of an MMU slot**, which is the P6.74/P6.78 defect class.
   ★★ **The argument that it is safe is that nothing inside the row loop remaps slots 5 or 6** —
   `prp_copy` uses fixed bases. **If anything is ever added to that loop, the cache must be
   revisited**; the `$FF` reset on entry is what keeps `prp_priority`'s remapping from poisoning it.
4. ★★★ **Region A is at 103 bytes.** P6.93 took 558, P6.95 72, this 48. **Two diagnostic arms are
   already blocked and the next addition to p3b meets this.**
5. ★★ **One room, one title, one window.** Span widths 6/13/42 are the castle's.
6. ★★ **`-ForceOverlap` and `-NoRestore` were not re-run.** Neither path changed shape, but AC-6
   names them.
