### 3 — Reasoning

**3.1 §3(2) — the acceptance test, in full, and why it was wrong.** The only test was:

```python
try:    cand = _to_cp1252(run).decode("utf-8")
except (KeyError, UnicodeDecodeError):  out.append(run)      # leave it
else:   out.append(cand); fixed += 1                          # "repair" it
```

★★★★★ **cp1252-encoding `U+00D7 U+2013` gives the bytes `D7 96`, and `D7` is a structurally valid
UTF-8 lead byte with `96` a valid continuation.** So the reversal decoded cleanly — to `U+05D6` — and
the repair wrote that into a correct report. ★★★★ **"Decodes as valid UTF-8" is necessary and not
sufficient, and on structure alone `D7 96` is INDISTINGUISHABLE from real two-byte damage.**

**3.2 ★★★★★ Why the length-based narrowing was REFUSED, and it is the load-bearing decision.** The
dispatch offered *"require the run to be ≥3 characters"*. ★★★★★ **That would stop catching damage to
every two-byte character — and `U+00D7` is one of them (`C3 97`).** §6's first trigger says **a checker
narrowed into silence is worse than one that false-positives**, so the length test is not used. ★★★
**Self-test case 1c exists solely to fail if anyone reintroduces it.**

**3.3 The narrowing that was taken.** The run's FIRST character must be the cp1252 decode of a UTF-8
lead byte **that the tree's characters actually produce**: `C2` and `C3` (Latin-1 Supplement — the
multiplication sign itself) and `E2` (`U+2000`–`U+2FFF` — the stars, box rules and dashes this harness
is full of). `U+00D7` decodes from byte `D7`, which leads the Hebrew block and nothing this project
writes. ★★ **Principled, not a heuristic — and its limitation is stated in the source**: damage to a
character whose lead byte is outside `{C2,C3,E2}` (CJK, astral planes) would go undetected, no file in
the tree contains one, and **if that changes the set must grow.**

**3.4 §2H's three checks.** (1) *A second mechanism for a different object class?* ★★★★★ **Yes, and it
is why Part A grew: the tool reports TWO conditions — a BOM and a double-encoded RUN — and they have
different truth values for MAME's own files.** Treating them as one is what would have forced either a
permanently-red gate or a blinded one. (2) *Name the calling routine.* The damage was not done by
`fix_mojibake.py` in isolation — **`run_gates.sh` printed it as advice**, so the caller is what turned a
false positive into a destroyed file. (3) *Grep the prior record.* T-P0-157 §4F supplied the diagnosis;
it was not re-derived.

**AC-3 [design] §1.3's answer about `co_checkctrl`, before Part B's implementation. ★★★★★ MET —
YES, and the reason is structural.**
```
co_cc_lp:   ldd co_ctrly / addd #1 / std co_ctrly     <- increments BEFORE reading
            ldx co_ctrloff / leax PRI_STRIDE,x        <- advances a row BEFORE reading
```
★★★★★ **It never touches the current row — only rows strictly below it — and it only READS.** A row
buffer for the current row cannot collide with it on any byte. ★★★★ **The deferred write-back is also
safe, and identically so to today's behaviour:** when row *N*'s walk descends, rows *N+1…* hold
pre-sprite values because the sprite has not drawn them yet, **which is exactly what per-pixel writes
produce now.** ★★ So `co_checkctrl` keeps its own `co_ctrloff` and its own `plane_pri` calls unchanged.

### 7 — Uncertainty flags

**7.1 ★★★★★ The narrowing's limitation is real and is stated in the source, not only here.** Damage to
a character whose UTF-8 lead byte is outside `{C2, C3, E2}` — CJK (`E3`–`E9`) or the astral planes
(`F0`–`F4`) — **will not be detected.** ★★★ No file in this tree contains one, **and if that changes the
set must grow.** ★★ A narrowing that silently stops covering something is the exact failure mode §6's
first trigger is about, so it is written at `_LEAD_OK` rather than left to a report.

**7.2 ★★★★★ A DISPATCH PREMISE FAILED: "a sprite row is at most 46 pixels — 23 packed priority bytes"
is wrong, and a 23-byte buffer would overflow on real game data.** `view_cel.s:579-583` already carries
both honest numbers:
- **Format bound: 255 pixels** — `VC_ROW_MAX equ 255`, because a cel's width is a single byte and *"no
  census can move it"*;
- **Corpus maximum: 115 pixels**, measured across seven titles (Kingquest2 view 130, SpaceQuest-1 view
  200).

★★★★ **115-pixel cels exist, and they need 59 packed bytes.** ★★★ This is L-85's distinction that
`view_cel.s` states explicitly, and **that file's own precedent is to size by the format bound**: *"this
is 255 because that is what the format permits, and the 140 bytes of difference are the cheapest
insurance in this file."* ★★ **129 bytes** (⌈255/2⌉+1, the +1 because a row can begin on an odd nibble
and touch one extra byte) is 12% of region A's headroom.
