### 4 — Verification (AC-by-AC)

**AC-1 [measured] §4A's buffer placement and the vector disposition. ★★★★★ MET, and all-RAM is never
entered.**

The observation that makes it free: **VOFFSET addresses PHYSICAL RAM, not the CPU's logical space**
[`gfx.s:206-215`; S-01 confirmed `$E800` → physical `$74000` empirically]. The GIME fetches the
framebuffer without going through the MMU, **so the buffer never has to be visible to the CPU all at
once — only the bytes being WRITTEN do.**

- Buffer at physical **`$74000`–`$7B7FF`** (blocks `$3A,$3B,$3C,$3D`), 30,720 bytes.
- Filled through logical **`$4000`–`$7FFF`**, remapping slots 2 and 3 **once** at the seam
  (30,720 < 32,768, so the seam is crossed a single time). ★★ B and Y carry across it, because
  16,384 / 160 = 102.4 and a source row straddles it.
- **Logical `$4000`–`$7FFF` is RAM under every map**, so nothing is written into ROM territory.
- ★★★★★ **`$FFDF` is never written. `$FFF0`–`$FFFF` keeps its ROM vectors.** **Nothing in this spike
  can produce an NMI through a garbage vector**, which is the false negative §1.2 exists to prevent.
- Code at `$3000` is slot 1 (block `$39`) and is never remapped; slots 2 and 3 are restored before the
  fill returns, so a host readback at `$4000` still sees the buffer's start.

### 4F — ★★★★★ A separate finding the HAL should have: VOFFSET's granularity is 256 BYTES

Sweeping VOFFSET with no HRES change:
```
VOFF $E800  (+0 bytes)    1,1,1,1,1,1,2,...   runs of 1: 175  runs of 2: 9
VOFF $E801  (+8 bytes)    1,1,1,1,1,1,2,...   IDENTICAL
VOFF $E810  (+128 bytes)  1,1,1,1,1,1,2,...   IDENTICAL
VOFF $E820  (+256 bytes)  1,1,1,1,1,2,...     SHIFTED by one row
```
★★★★★ **`+8` and `+128` are byte-identical; only `+256` moves anything. The register's low 5 bits are
ignored, so the framebuffer can only be positioned on a 256-byte boundary.**

★★★★ It fits MAME's fetch expression, recorded in full because `gfx.s` does not have it:
```cpp
offset += get_data((m_video_position + ((base_offset + offset) & 0xff)) | bank_512k, &data, &mode);
//  base_offset = m_legacy_video ? 0 : (m_gime_registers[0x0f] & 0x7f) * 2;   <-- $FF9F, HOFFSET
```
★★★★★ **The COLUMN offset supplies the low byte of every fetch address, and `$FF9F` is added into it.**
★★★ So `$FF9F` is not merely *"HOFFSET = 0 (REQUIRED)"* as `gfx.s:221-223` has it — **it participates
in the fetch address on every byte**, and a nonzero value shifts the picture horizontally within a
256-byte window.

★★★★ **This does NOT contradict `physical >> 3`** — S-01 proved `$E800` → physical `$74000`. **It says
the low bits of that quotient do not reach the hardware.** ★★★ It is squarely the territory of
`gfx.s:212-213`'s undischarged debt (*"inferred from disassembly; NOT verified… discharge by sentinel
test"*), and **it is the closest thing this series has produced to discharging part of it** — but it is
a MAME measurement, not a silicon one, and **it is carried as a finding, not applied** (nothing under
`src/`).

### 7 — Uncertainty flags

**7.1 ★★★★★ The row repeat is characterised but NOT diagnosed.** Reproducible, periodic, ~9 per frame,
`$1E` only, independent of any mid-frame write, with the fill verified and the palette clean. **Cause
unknown.** ★★★ Everything checked is listed under AC-3 so the next reader does not re-check it.

**7.2 The §4B(2) instrument is weaker than S-02's, and its ABSOLUTE POSITIONS ARE WRONG.** ★★★★★ The
4-colour control put the 1→2 transition at run index 171 (≈ scanline 196), but `dly 2400` places the
boundary near **y=123** — where S-02's absolute decode found it and where the stripe transition profile
independently puts it. **Only the 1-vs-2 PATTERN may be read from this instrument, never a scanline
number.** ★★★ The repeat finding rests on the pattern, so it survives; **a later task must not quote
this instrument for a position.** Why the positions are wrong is not established.

**7.3 ★★★★ A HYPOTHESIS that reaches past this spike, with a cheap test, and it is NOT this spike's to
run.** `$1E` is the mode the port uses for its main display today [`hal.inc:328`]. If MAME shows one
framebuffer row twice in that mode, **the port's rendered picture is slightly vertically compressed and
its byte gates cannot see it** — they compare the FRAMEBUFFER, and *"a readback path and a display path
are different paths"* [idiom 19j; AD-114 was exactly a case where both planes were byte-identical and
never presented]. ★★★ **The test:** compare a picture-gate framebuffer against the rendered screen row
by row, or point this instrument at the port's own display — **noting that on real picture content two
genuinely identical adjacent rows are indistinguishable from a repeat, so the port test needs a
synthetic pattern, not a game screen.** ★★ **If it holds it is a finding about every eye gate this
project has passed. If it does not, something about this spike's configuration provokes it.**

**7.4 Reading emulator source has a diminishing-returns point and it was reached.** The first read gave
the per-scanline recording mechanism (S-01) and the fetch expression (§4F). ★★★ **The third and fourth
returned plausible-sounding mechanisms that do not survive arithmetic** — `(base_offset + offset) &
0xff` was offered as the cause and is a no-op for offsets 0..159. ★★ **A summary of source is not
source**, and the difference showed up as confident prose with no quotable line behind it.

**7.5 ★★★★★ AC-7's EYE GATE WAS NOT RUN.** S-01 and S-02 each put their result on a screen at normal
speed against a stated expectation, and the dispatch says that is *"what makes the results credible"*.
★★★ **S-03's results are host-side numbers with no human confirmation.** The 16-colour split and the
three-band screen are both eminently watchable and **should be shown before any of this is built on.**

**7.6 Three instrument defects, all found by the liveness witness naming the guest.** ★★★★ The
16-colour fill re-read its mode and fill byte **per byte** (~50 cycles × 30,720 = **over 50 frames**), so
the host sampled a half-filled buffer and read `s01_frames = 0`; the host then waited a **fixed frame
count** after a refill ack that means *"request received"*, not *"fill finished"* — it now waits for
completed loop iterations, **a positive signal rather than an assumption**; and added code pushed short
branches out of reach, now long rather than marginally short. ★★ **Third, fourth and fifth defects in an
instrument this series keeps having to repair, and every one was caught by a witness rather than by
inspection.**
