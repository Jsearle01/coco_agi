### 1 — Summary

★★★★★ **Wiring is blocked by a coupling in the table generator, not by size and not by the text
engine.** `gen_vm_tables.py:225` reads


So the moment `vmop_print` exists as a label anywhere in that glob, **the single generated

### 3 — Reasoning

**3.1 ★★★★★ The mechanism, exactly.**

Three facts compose into the blocker, and each is fine alone:

1. **`vm_tables.s` is generated and shared.** Its header: *"GENERATED by gen_vm_tables.py. DO NOT
   EDIT."* All three VM-bearing probes include the same file.
2. **A defined label beats `modelled`** [`gen_vm_tables.py:225`]. This is deliberate and correct: it
   is what lets an opcode graduate from declared-no-op to implemented without editing two places.
3. **The scan is global** [`implemented_labels(src_dir)` globbing `vm_*.s`]. It asks *"does this
   label exist in the source tree?"*, never *"does this build link it?"*

★★★★ **Together they mean the table has exactly one configuration, and the configuration is a
property of the tree rather than of the build.** ★★★ **There is no way to define a handler for one
probe only** — which is precisely what wiring the text opcodes requires, because `text.s` fits in the
new probe's ruled span and not in `p3b_probe.s`'s one spare byte.

**3.2 ★★★★ What I checked before concluding it was structural.**

- **Put the handlers where the scan cannot see them** (`src/engine/`, or a name not matching
  `vm_*.s`). ★★ Then the generator never binds them and the table keeps `vm_op_modelled` — **not
  wired at all.** The visibility that causes the problem is the same visibility that does the wiring.
- **Indirect through a vector**, so the handlers live in a shared file with bodies that are inert
  unless a probe installs a pointer. ★★★ **Still costs p3b bytes it does not have**: a shared
  trampoline is ~4 bytes per handler plus a dispatcher, ~46 B against **1**.
- **Change the reference instead.** ★★★★ Irrelevant, and this is the sharpest finding of the three:
  **the nine entries bound with the Python leg completely untouched.** Status is only consulted when
  no label exists (`elif st == "modelled"`), so `modelled` is a *fallback*, not a gate. **§2V's
  "both legs move together" is not what governs here** — the label alone moves the 6809 leg.

**3.3 ★★★ Why the experiment was worth running rather than reasoning through.**

The coupling is visible in the generator's source, and I could have argued it from `line 225`.
★★★ **This project has been wrong four times about mechanisms read from source in this exact
subsystem**, and §2W's rule is that a claim gets believed when the failing case has been *seen*. The
experiment cost one file, one regeneration and two assembles, and it produced the actual error text
rather than my paraphrase of it. ★★ **It also confirmed the reverse direction**: removing the file
and restoring the table returns `p3b_probe.bin` to `F51FF848…` byte-for-byte, so the coupling is
exactly and only what was demonstrated.

**3.4 ★★ Three ways forward, named and NOT chosen.**

★★★ **§7 trigger 5 says stop, and §11 forbids me proposing a new layout.** These are stated so the
ruling can be made, not to pre-empt it:

| | what it costs |
|---|---|
| **(a) Free space in `p3b_probe.s`** and give all probes the handlers | ~1,608 B needed against 1 spare; `MAP_CODE` is frozen by §11 — **needs a layout ruling** |
| **(b) Make the generator emit per-configuration tables** (e.g. a `--with-text` variant, or an `ifdef`-guarded entry) | changes the generation contract and creates a second table to keep in sync; the drift check exists and would have to cover both |
| **(c) Accept that `p3b_probe.bin` moves** and re-baseline the P3b gate | **exactly what trigger 5 exists to prevent**; every prior P3b figure would need qualification |

★ **(b) looks smallest from here and I am not choosing it** — it touches the mechanism whose whole
value is that a table cannot be configured per-repo, and that is an architecture decision.

**3.5 ★★ §2H's three checks.**

1. **A second mechanism for another object class?** ★★★ Yes, and it is the finding: **opcode status
   has two mechanisms** — the reference's `modelled` classification and the assembly's label
   existence — and **the second silently outranks the first.** A reading of `commands.py` alone
   (where all nine sit in an explicit MODELLED list) would say the Python leg is the gate. It is not.
2. **The calling routine.** `implemented_labels`'s caller is `build()`, which runs **once per tree**,
   not once per probe. **The enclosing fact is the scan's scope**, and that is the whole defect.
3. **Grep the reports for the same subsystem.** P6.28 §5A established `p3b_probe.s`'s spare as **1
   byte** against the dispatch's 46 — ★★★ **and that correction is load-bearing here**: at 46 bytes
   a nine-`rts` stub would have fit, the coupling would have surfaced later as a `text.s` size
   overrun, and the diagnosis would have been "too big" rather than "wrongly coupled."

**3.6 ★★ Authority tier.** No ScummVM or Specs claim. Every figure is `lwasm` or `gen_vm_tables.py`
output on this tree at this HEAD.

### 7 — Uncertainty flags

1. ★★★★ **The blocker is demonstrated for the label mechanism; I have not proven no fourth route
   exists.** §3.2 examines three and rejects each with a measured number, but *"there is no way"* is
   a stronger claim than *"these three do not work"*, and only the second is established.
2. ★★★ **`text_vm_probe.s`'s glue is still an estimate** (P6.28 §7.1, ~927 B by arithmetic). The
   ruled placement was never exercised, so **the ruling remains unvalidated by an assembly**.
3. ★★★ **A design problem is visible and not diagnosed: `text.s` addresses the framebuffer through a
   window** (`txt_fbwin` / `txt_fbrow0` / `txt_fbrows`, 5 character rows per 8 KB slice). ★★ At
   1,280 B per character row, **rows 6 and 12 straddle slice boundaries — and both are inside the
   scroll panel's rows 6–18.** A naive per-slice blit would leave two blank rows. ★ Mapping three
   visible-plane blocks into slots 4–6 gives a flat 24 KB window covering rows 0–18 with no straddle,
   which looks like the answer; **it is untested and is recorded as a hazard the wiring task will
   meet, not as a solution.**
4. ★★ **Whether `display` changes diffable state is unmeasured.** The reference's `TextRenderer` is
   never instantiated by `Vm` (`cycle.py` has no `TextRenderer(`), so implementing the Python leg is
   a real addition, not a re-point — and trigger 4's condition cannot be assessed until it exists.
5. ★ **`-DPLANE_WINDOWED -DPRI_PACKED` remains carried unexamined** (P6.28 §7.4, and §2 of this
   dispatch asked for it). Not reached.
