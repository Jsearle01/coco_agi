### 1 — Summary
`tools/agivm/` executes AGI LOGIC bytecode and emits the oracle's own per-cycle dump format;
`harness/tools/vmdiff.py` diffs the two. Against the pinned oracle, over three titles and every
one of the 256 variables and 256 flags at every cycle: **all variables match for the whole run
in all three titles**, and each title diverges on **exactly one flag**. That is one defect with
three symptoms, not three — each divergent flag is a completion flag the *interpreter* sets when
an animation or motion finishes, which needs the VIEW parser and motion system this VM declares
it does not have. Before any of that could mean anything the oracle had to be made
deterministic, which turned out to be the more consequential half of the task: its in-game timer
ran on wall-clock milliseconds, and the fix removes the nondeterminism at source rather than
excluding its consequences, leaving the diff's **exclusion set empty**.

**3.1 The four pre-dispatch grep items, as MEASURED.**

Opcode counts, counted at the pin rather than quoted:

| table | lines | entries |
|---|---|---|
| `opCodesV1Cond` | 34–52 | 17 |

V2 tests + commands = **203**; all four tables = 319. Both match the Orchestrator's figures.

★ **§2H applied to the figure itself.** 183 is the count of table *slots*, not of behaviours:
the table holds **181 distinct handlers**, one `nullptr` (`return`, dispatched inline by the
interpreter loop and never through the table), and **two entries sharing `cmdDiscardView`**.
"183 opcodes to implement" would be wrong in both directions.

**VM-state dump conventions** (`oracle/patches/0002`): one line per cycle, emitted at **cycle
ENTRY** before the cycle acts, as `cycle %06u flags <32 bytes hex> vars <256 bytes hex>`.
`MAX_FLAGS` is `256>>3` = 32 bytes packed LSB-first within each byte — read at `global.cpp:33-48`
(`flagPtr += flagNr >> 3; *flagPtr |= 1 << (flagNr & 0x07)`), not assumed. Written via
`Common::DumpFile`, which renames on close, so a `timeout`-killed run leaves `vmstate.txt.tmp`.

**Clock-coupled values** — and this is where the first-mechanism reading was wrong.

**3.2 ★★ The clock-coupled set is not var 11, and excluding it was the wrong fix.**
`inGameTimerUpdate()` (`global.cpp:231`) derives vars **11, 12, 13 and 14** from
`getTotalPlayTime()` — real wall-clock milliseconds. Authority: ScummVM source at the pin.

Measured on the **unmodified** oracle, kq4dem, 20 s, idle run vs a run under 3×-nproc load:
vars **11, 72, 73** diverge (first at cycles 38, 39, 39). That reproduces T-P0-003's finding and
explains it — 11 is the clock, 72/73 are kq4dem script values tracking it. Vars 12–14 did *not*
diverge only because 20 s never crosses a minute (**L-22**: the retrieved set is not the whole set).

★ **Two idle runs do not show any of this.** The pacing gate (`cycle.cpp:449`) keeps cycle N
pinned to wall time N/40 on an unloaded machine, so an idle pair is byte-identical and *looks*
deterministic. The load is what makes the coupling observable. An idle-only determinism check
cannot fail and therefore establishes nothing (**L-23**).

The obvious move — exclude 11/72/73 — is the wrong trade: **72 and 73 are ordinary game
variables**, and excluding them puts real interpreter state permanently outside the gate to work
around a harness defect. Patch 0005 instead replaces the wall-clock timer with a virtual clock
advancing 25 ms per main-loop iteration — the unit the pacing gate already counts in. Same
idle-vs-loaded comparison afterwards, 807 common cycles: **all 256 vars and all 256 flags
identical. Exclusion set EMPTY.**

★ §2.1: patch 0005 is a **deviation from the oracle**, adopted for determinism. It is not a claim
about Sierra's interpreter. It sits closer to the CoCo3 target, whose clock will be a 60 Hz VBL
count, but that is a convenience and not the justification.

★ **RNG**: `Common::RandomSource` seeds from the time of day unless `random_seed` is set, and
`--random-seed=N` is a first-class CLI option (`base/commandLine.cpp:187,932`) — so no patch was
needed. Runs now pass a fixed seed. **Not established:** whether kq4dem consumes the RNG at all.

**3.3 The dispatch table is BUILT, not loaded (§2H).** `setupOpCodes()` (`opcodes.cpp:372`) does
not load a static table — it copies a base and mutates it by interpreter version, platform,
gameID and **feature flags**. Measured against the pinned corpus (194 classified rows,
cross-referenced with `detection_tables.h`):

- **version-driven** mutations fire for **zero** rows — every pinned version (0x2272, 0x2440, 0x2917, 0x3149) sits above every threshold in `setupOpCodes()`;
- **feature-driven** for **21 rows, all fanmade** — `GF_AGIMOUSE` (18) and `GF_AGI256` (4, one row carrying both);
- **platform/gameID** for none — the corpus is CoCo3 / PC-DOS / fan.

So for the CoCo3 and Sierra DOS titles this project targets the table is effectively static — but
that is a **measured result about this corpus**, not a property of AGI, and `dispatch.py`
**refuses** a configuration it cannot run rather than silently using the base table.

**3.4 ★★ Generated, not typed — because typing them failed.** I first hand-wrote the VM constants
from memory. Four `VM_VAR_*`/`VM_FLAG_*` names or values were wrong
(`VM_VAR_WINDOW_AUTO_CLOSE_TIMER` became "WINDOW_RESET", `VM_FLAG_MENUS_ACCESSIBLE` became
"MENUS_WORK", the list stopped at 26 and missed three mouse vars, and one line was corrupted
outright), and the **entire `ViewFlags` bit assignment was inverted** — `fDrawn` is 0x0001 and
`fAnimated` 0x0040; I had them the other way round. **None of these raise.** They silently
address the wrong variable or test the wrong bit. `gen_oracle_tables.py` now generates all of it
from the pin, and `--check` exits 1 on drift (proven by breaking it, **L-27**).

**3.5 A real defect in the tracked oracle runner.** `oracle_dump.sh` runs under `set -e`, and the
**expected** exit code from `timeout` is 124. The script aborted the instant ScummVM was killed,
so the rename never ran and every long-lived dump stayed a `.tmp`. Measured on Kingquest1: three
header lines printed, then nothing, and `vmstate.txt.tmp` sat unrenamed. The `[ -f ]` test in the
rename loop had the same problem. Fixed and annotated with the measurement.

**3.6 §2.1 — normalisations NOT reproduced.** ScummVM carries game-specific workarounds inside
opcode bodies. They are deliberately not transcribed, and each is flagged in `commands.py`:
`cmdDistance`'s KQ4 zombie workaround (ScummVM's own comment says the bug "also happens in the
original interpreter", so reproducing it would reproduce a **ScummVM fix**, not AGI behaviour);
`newRoom`'s LSL1 flag-36 and KQ3 flags-193..197 workarounds and the Gold Rush copy-protection
redirect. For those four titles a state diff **will** diverge here, and that divergence is
correct rather than a defect.

★ One place where code and comment disagree: `cycle.cpp:377` sets `VM_FLAG_LOGIC_ZERO_FIRST_TIME`
with the comment "not in 2.917", but sets it unconditionally — and the oracle dump for a 2.917
game confirms it is set. Followed the code (§2 ranks comments lowest).
